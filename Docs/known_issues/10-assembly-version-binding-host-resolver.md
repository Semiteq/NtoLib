# Хост перекрывает несовпадение версий strong-name (внешние NuGet-зависимости)

## Описание проблемы

`NtoLib.dll` может держать **внешнюю** ссылку на strong-named NuGet-сборку, версия
которой не совпадает с той, что физически лежит рядом с DLL в папке MasterSCADA. По
правилам загрузчика .NET Framework это должно давать `FileLoadException` в рантайме, но
на практике не даёт — хост MasterSCADA перекрывает бинд собственным резолвером. Дрейф
версий поэтому невидим в разработке и проявляется только в продакшене.

**Внешняя зависимость** — запись в exclude-листе `NtoLib/ILRepack.targets`: такая сборка
не входит в merge и разрешается загрузчиком по обычным правилам. Механизм ниже разобран
на `System.Text.Json` и относится к любой внешней strong-named зависимости.

## Механизм: почему внешняя ссылка не падает на несовпадении версии

Для strong-named ссылки (ненулевой `PublicKeyToken`) загрузчик .NET Framework требует
**точного совпадения версии** манифеста с версией ссылки (после применения возможных
binding redirect). Если рядом лежит только сборка младшей версии и редиректа нет →
`FileLoadException`, HRESULT `0x80131040` («manifest definition does not match the
assembly reference»).

MasterSCADA — плагин-хост, грузящий множество сторонних .NET-компонентов, — ставит
**process-wide `AppDomain.AssemblyResolve`, резолвящий по простому имени** (файл в папке
установки). Ключевой факт: **сборка, возвращённая из `AssemblyResolve`, принимается
загрузчиком в обход проверки версии strong-name.** Ссылка на старшую версию связывается с
файлом младшей. Пока код не выходит за API-уровень младшей версии, всё отрабатывает.
Своего `AssemblyResolve` у NtoLib нет — резолвер хостовый, ставится на старте AppDomain,
задолго до JIT методов NtoLib.

### Воспроизведение

net48-экзешник, скомпилированный против `System.Text.Json 10.x`, в папке, где рядом
только хостовые `4.x` (STJ `4.0.1.2` + её транзитивные зависимости):

| Случай | Настройка | Итог |
|--------|-----------|------|
| A | сырой бинд, без резолвера | `FileLoadException 0x80131040` — версия не сошлась |
| B | `AssemblyResolve` по простому имени, поставлен до JIT метода-потребителя | резолвер отдаёт `4.0.1.2` → **`OK`, `JsonSerializer resolved to v4.0.1.2`** |

Тонкость случая B: резолвер обязан стоять **до** JIT-компиляции метода, который трогает
зависимость. JIT резолвит зависимости при компиляции всего тела метода, поэтому нельзя
ставить хендлер и вызывать сборку в одном методе — бинд произойдёт раньше установки
хендлера. Хост ставит резолвер на старте AppDomain, задолго до джита методов NtoLib.

## Почему внешняя ссылка — ловушка

Внешняя strong-named ссылка работает, пока держатся два контракта, **невидимых для
xUnit** (в dev NuGet кладёт настоящую сборку рядом, ссылка резолвится штатно, тест
зелёный):

1. Каждая версия хоста ставит резолвер по имени и поставляет совместимую версию сборки.
   Уберёт резолвер, переедет папка, сменится модель загрузки — бинд упадёт
   `FileLoadException 0x80131040`, уже в продакшене.
2. Код не выходит за API-уровень хостовой версии. Вызов из более новой версии (для STJ:
   позиционные `record` при десериализации, `JsonNode`, source-gen,
   `JsonSerializerOptions.Default`) на старой сборке даёт `MissingMethodException` /
   `MissingFieldException` в рантайме — тесты на новой версии этого не поймают.

Симптом — не MOTW (`0x80131515`, см. [04-deployment-errors.md](04-deployment-errors.md)),
а `FileLoadException 0x80131040` (версия) либо `MissingMethodException` (API), уже после
успешной регистрации, в момент первого обращения к соответствующему коду.

## Политика NtoLib

Зависимости делятся на два класса по признаку merge. Предусловие механизма выполняется
только для внешнего класса.

| Класс | Где живёт | Бинд | Члены |
|-------|-----------|------|-------|
| Mergeable | внутри `NtoLib.dll` (вне exclude-листа) | приватная копия версии, против которой собран код; хостовая версия в бинде не участвует, оба контракта к таким зависимостям не применяются | `System.Text.Json`, `System.Text.Encodings.Web` |
| Не-mergeable | внешняя, файлом рядом с DLL (в exclude-листе) | ломается при интернализации; разрешается хостом, используемый API ограничен хостовым уровнем | `System.Resources.Extensions` |

Интернализация безопасна, потому что типы зависимости не пересекают COM-границу к хосту:
NtoLib использует их для себя. Единственный потребитель `System.Text.Json` в коде —
`OpcTreeManager` (`Config/TreeSnapshotWriter.cs`, `Config/TreeSnapshotLoader.cs`).
Ограничения не-mergeable класса — в [02-dll-merge-constraints.md](02-dll-merge-constraints.md).

Для любой внешней зависимости, завязанной на хостовую версию, используемый API
ограничивается уровнем этой версии и фиксируется (тест/линт) — иначе дрейф API проявляется
только в продакшене.

## Диагностика

Ground-truth-проверка, что и откуда связалось в хосте — Fusion binding log:

```
reg add "HKLM\SOFTWARE\Microsoft\Fusion" /v ForceLog /t REG_DWORD /d 1 /f
reg add "HKLM\SOFTWARE\Microsoft\Fusion" /v LogFailures /t REG_DWORD /d 1 /f
reg add "HKLM\SOFTWARE\Microsoft\Fusion" /v LogPath /t REG_SZ /d "C:\FusionLog\" /f
```

Перезапустить MasterSCADA, выполнить операцию, затронувшую нужный код, посмотреть логи в
`C:\FusionLog\`. По завершении диагностики удалить эти ключи (`ForceLog` замедляет
загрузку сборок во всей системе).

Статическая проверка внешних ссылок смёрженной DLL:

```powershell
([Reflection.Assembly]::ReflectionOnlyLoadFrom('NtoLib.dll')).GetReferencedAssemblies() |
  ForEach-Object { '{0}  {1}' -f $_.Name, $_.Version }
```

Интернализированная зависимость в этом списке отсутствует; внешняя — присутствует с
запрошенной версией.

> Примечание: `dotpeek`/статические анализаторы резолвят зависимости по простому имени и
> **игнорируют версию strong-name** — «битых зависимостей не найдено» у них не доказывает,
> что рантайм-бинд по версии сойдётся.
